# Phase 1 技术障碍分析和解决方案

## 当前状态 🚧

### 已尝试的方案

#### 方案 A: 绕过 PointNet2，直接加载 PTV3
**结果**: 失败 ❌

**遇到的问题链**:
1. GraspGenGenerator → 触发 PointNet2 导入
2. 尝试直接加载 PTV3 → 需要 `timm` ✓ (已安装)
3. PTV3 → 需要 `spconv` (Sparse Convolution) ❌
4. spconv 是另一个复杂的 C++ CUDA 扩展库

**根本原因**:
- 上游 GraspGen 的预训练模型使用 PTV3 backbone
- PTV3 依赖 spconv (稀疏卷积)
- spconv 需要编译 CUDA C++ 扩展
- 即使编译成功，稀疏卷积算子**无法导出到 ONNX**

### 技术障碍总结

```
GraspGen 预训练模型
    ↓
PTV3 (PointTransformerV3)
    ↓
spconv (Sparse Convolution)
    ↓
CUDA C++ 扩展 + ONNX 不兼容
    ↓
❌ 无法导出
```

## 问题本质 🔍

**核心矛盾**: 
- 上游 GraspGen 使用的架构（PTV3 + spconv）是为 GPU 训练优化的
- 这些组件依赖 CUDA 自定义算子，**不兼容 ONNX 导出**
- S600 BPU 需要标准 ONNX 算子

**类似案例参考**:
- FoundationPose-s600: 使用标准 PyTorch ResNet backbone（成功）
- SAM_s600: 使用标准 ViT（成功）

## 可行解决方案 💡

### 方案 D: 使用简化的纯 PyTorch PointNet（推荐）⭐

**思路**: 
1. 实现或使用第三方纯 PyTorch PointNet（无 CUDA 扩展）
2. 微调或迁移学习适配到 GraspGen 任务
3. 确保完全兼容 ONNX

**优势**:
- ✅ 完全兼容 ONNX 导出
- ✅ 无 C++ 扩展依赖
- ✅ 适合 BPU 编译

**劣势**:
- ⚠️ 需要重新训练或微调
- ⚠️ 可能精度略低于 PTV3
- ⏱️ 时间成本：3-5 天

**实施步骤**:
1. 使用 PyTorch3D 或其他纯 PyTorch PointNet 实现
2. 冻结上游 Diffusion Head 权重
3. 仅训练 PointNet encoder
4. 在少量数据上快速验证

### 方案 E: 切换到基于图像的方法

**思路**: 
- 使用深度图 + RGB 作为输入
- 替换点云编码器为 CNN/ViT
- 利用现有的图像处理工具链

**优势**:
- ✅ 成熟的 ONNX 导出工具链
- ✅ 丰富的预训练模型
- ✅ BPU 对图像模型优化更好

**劣势**:
- ⚠️ 需要重新设计输入 pipeline
- ⚠️ 可能丢失 3D 几何信息
- ⏱️ 时间成本：5-7 天

### 方案 F: 请求上游提供 ONNX 友好模型

**思路**:
- 联系 NVlabs/GraspGen 作者
- 请求提供使用标准 backbone 的预训练模型
- 或询问 ONNX 导出的最佳实践

**优势**:
- ✅ 官方支持
- ✅ 保证精度

**劣势**:
- ⏱️ 响应时间不确定
- ❓ 可能不提供此类模型

### 方案 G: 分阶段适配（混合方案）

**阶段 1**: CPU/GPU 原型验证（当前 Phase）
- 在 ws-wan 上使用原始 PTV3 模型
- 编译 spconv 扩展（仅用于验证）
- 验证算法流程和精度基线
- **不导出 ONNX**

**阶段 2**: 替换 backbone（Phase 2）
- 使用纯 PyTorch PointNet 替换 PTV3
- 迁移学习或微调
- 导出 ONNX 并编译 HBM

**优势**:
- ✅ 快速验证算法可行性
- ✅ 分离架构问题和精度问题
- ✅ 灵活调整策略

**劣势**:
- ⏱️ 总时间更长
- 🔄 需要两个版本的模型
